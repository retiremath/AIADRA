# AIADRA Glossary

Definitions of terms that recur in AIADRA discussions, specs, and code. The point is to stop re-litigating terminology in every conversation. Where a term's meaning is still open, the entry says so.

This is a **working document**. Entries are expected to gain precision over time. When a term's meaning is later pinned by an ADR, this glossary should be updated to match.

---

## Core concepts

**AIADRA** — The project itself. Treat as a brand name; pronounced /ai-AH-dra/. Per [ADR/0027](ADR/0027-aiad-positioning-and-native-engine-posture.md), AIADRA is positioned as an **AIAD platform** (see AIAD below) — distinct from CAD as a system category. The full product-engineering scope (mechanical, electrical, software, procurement, V&V, documentation, requirements) is what "Design" in AIAD names; the name AIADRA stands on its own as the project's brand.

**AIAD** — *AI-Augmented Design.* A system category distinct from CAD (Computer-Aided Design). In CAD the computer is a tool that aids the human; in AIAD, AI is a structural engineering participant — AI proposes; the deterministic core validates; humans approve (Manifesto P2 + P5). "Design" here is category-language for the whole product-engineering authoring loop, not CAD/drawing-only scope. Pinned by [ADR/0027 §0](ADR/0027-aiad-positioning-and-native-engine-posture.md).

**AIADRA Core** — The library, CLI, and tooling that we maintain under the AIADRA project. Distinguished from any future ecosystem projects (registries, hosted validators, shared part libraries) that may consume AIADRA but are not part of the core. Per Manifesto Principle 11, AIADRA Core hosts nothing.

**Product Truth Model** — The canonical, authoritative representation of a product as a graph of engineering Objects, relationships, parameters, requirements, events, and history. Everything else — files, exports, drawings, dashboards, AI views — is a projection of this model. Current architectural instinct (open until `ADR/0001`): the Truth Model is realized as canonical text artifacts (sidecars + event log + manifests) in the project's Git repo, with binary artifacts in a pluggable Vault and a local derived acceleration cache.

**Object (Managed Object)** — An engineering entity tracked as a first-class managed artifact in the Product Truth Model, with stable UUID identity, Number, Type, and metadata. The Promotion Rule in [TruthModelSchema.md](TruthModelSchema.md) determines which entities qualify. Current catalogue (as of TruthModelSchema v0.6):

- **Seed Object Types** (pinned by [ADR/0003 §1 / §2](ADR/0003-schema-governance.md) named examples): Part, Requirement, Assembly.
- **Tier-2 Object Types** (cleared the rule; per-Type ADRs landed [ADR/0017](ADR/0017-object-type-drawing.md) Drawing, [ADR/0019](ADR/0019-object-type-evidence-artifact.md) EvidenceArtifact, [ADR/0020](ADR/0020-object-type-test-procedure.md) TestProcedure — all three Tier-2 candidates now promoted).
- **Candidate pool, deferred** (pass the capability test plausibly; deferred until concrete use case or [OQ-0016](OpenQuestions.md) reopening): Supplier, Component (purchased item), Software module, Electrical component.
- **Recognized non-Objects** (handled by other spine artifact kinds): Feature (CAD construction-history) as records under parent Part; Test execution / Evidence citation / measurement as records under their parent; Release as Release Manifest + release transaction + events (optional derived Release index for query ergonomics); ECR / ECO as externally governed workflow artifact in the Git host, referenced via PR URL / commit hash; AI Decision as event payload (reopenable through [OQ-0003](OpenQuestions.md)); BOM and similar derived reports (where-used, dashboards, trace matrices, validation summaries, impact-analysis reports, generated exports) as D7-disqualified derived views.

**Native Engine** — An AIADRA-implemented, AIAD-native authoring runtime for a specific domain (mechanical, electrical, etc.). Native Engines use third-party kernels and libraries (OCCT for mechanical geometry; KiCad's reusable libraries for electrical; etc.) as dependencies, but **never wrap third-party applications** — FreeCAD-the-application, KiCad-the-application, Solvespace-the-application are research material, not implementation dependencies. Native Engines emit canonical Objects, events, and Vault blobs directly against the Product Truth Model. Ship as ecosystem packages outside `aiadra-core` (`aiadra-mechanical`, `aiadra-electrical`, etc.) per [ADR/0027 D11](ADR/0027-aiad-positioning-and-native-engine-posture.md). Replaces the prior "Domain Engine" entry per [ADR/0027 D5](ADR/0027-aiad-positioning-and-native-engine-posture.md).

**Data Adapter** — Lighter-weight Layer 5 category for domains that are pure data flow (no parametric authoring): format converters, external-tool data ingestion (DOORS / Polarion / ReqIF bridges for requirements; CSV/instrument-data importers for DV results), BOM exports, procurement-API consumers. Distinguished from Native Engine (which has its own parametric authoring surface) per [ADR/0027 D12](ADR/0027-aiad-positioning-and-native-engine-posture.md). May be ecosystem packages or optional core extras. Replaces the prior "Domain Adapter" entry per [ADR/0027 Q10](ADR/0027-aiad-positioning-and-native-engine-posture.md).

**AI Action Protocol** — The set of stable structured contracts through which AI agents (and other automation) interact with AIADRA: `inspect`, `query`, `propose`, `modify`, `simulate/check`, `validate`, `explain`, `commit/rollback`, `release`. AI never reaches around these contracts to touch raw files or kernels directly.

## Three-tier architecture

AIADRA inherits Windchill's Commonspace / Vault / Workspace separation, realized on top of Git and a pluggable blob store (Manifesto Principle 12).

**Commonspace** — The project's shared, official, governed record. Realized as the Git remote — `origin/main`, protected branches, signed tags, the change-order pipeline gating writes. Holds canonical text artifacts (sidecars, event log, release manifests) and references (by content hash) to Vault blobs. Released revisions live here. Every Workspace clone contains a local mirror of Commonspace within its fetched scope.

**Vault** — Pluggable storage for large binary artifacts: STEP exports, mesh files, drawings, PDFs, simulation outputs, renders. The repository holds references and hashes; the Vault holds the bytes. Default Vault implementation is GitHub LFS; pluggable alternatives include S3 / MinIO, IPFS, NAS, project-local filesystem, via the Vault Adapter contract. The Vault is blob storage only — it holds no engineering decisions, no events, no metadata that belongs in the Commonspace text record.

**Vault Adapter** — The contract any blob backend must implement to serve as a Vault: content-addressable read/write by hash, presence-check, fetch, garbage collection cooperation. AIADRA Core ships at least one default adapter (GitHub LFS) and project maintainers may configure others. The adapter is the only place Vault choice leaks into the rest of the system.

**Workspace** — A developer's local environment: the Git clone + working tree + live Native Engine sessions / Data Adapter processes currently active. Per-developer, high-bandwidth, where work-in-progress and AI activity live. The Workspace is the natural operating context for AI agents (Manifesto Principle 13).

**Workspace Browser** — The UI through which a human (and AI) inspects and manipulates the Workspace. **Primary Workspace Browser is AIADRA Studio** — a standalone desktop authoring app (Creo-style 3D viewport + Windchill-style Product-Truth data panel) per [ADR/0032](ADR/0032-aiadra-studio-scope.md). **VSCode + the AIADRA extension remains a secondary developer/agent integration surface** (code, docs, reviews, agent workflows). AIADRA Native Engines (`aiadra-mechanical`, `aiadra-electrical`, ...) present domain-specific authoring surfaces over the same Workspace state, which Studio drives via the Ring 2 protocol. (Amended from VSCode-primary per ADR/0032, arc 20260602-5; v0.25 → v0.26.)

## Locality and synchronization

**Locality tier** — Where data physically resides relative to a given Workspace. Three tiers:
- **Always-local.** Text artifacts in the current checkout (working tree). Free, instant.
- **Local-if-fetched.** Other branches, LFS pointer-resolved blobs, history beyond shallow-clone depth. Free if already pulled; one fetch otherwise.
- **Remote-only.** Untracked branches, never-fetched blobs, refs not yet pulled. Requires a `git fetch` or `git lfs pull`.

AI queries and AIADRA Core APIs declare what locality they require; the system reports what is already local and what would need to be fetched.

**Staleness tolerance** — A property of a read operation: is it correct to answer from the Workspace's local mirror of Commonspace (possibly out of date), or must the local mirror first be synchronized? Most queries tolerate staleness (looking up the prior parameter value, the release history, the where-used graph). A few do not (generating a release manifest against the *current* released revisions). AIADRA Core exposes this distinction at the API surface so callers choose deliberately.

**Reservation file** — A schema-governed canonical artifact recording Number allocations for one Object Type prefix per [ADR/0004](ADR/0004-number-allocation.md). One Reservation artifact per prefix at `Docs/Reservations/<TypePrefix>.yaml`; the Number is the YAML mapping key so duplicate claims collide at parse time via the AIADRA YAML Profile's duplicate-key rejection. Each entry binds a Number to an Object UUID with status `current` or `retired` plus audit metadata; retired entries are permanent aliases per [S2.5 commitment 7](TruthModelSchema.md#7-number_rebound-retires-the-old-number-as-an-alias). Allocations are Transaction-atomic across sidecar + event + Reservation per ADR/0004 §6 — the Layer-2 validator hard-rejects any commit touching a Reservation entry without the full coherent set. Conflict resolution at PR time via Git rebase per [S2.5 commitment 3](TruthModelSchema.md#3-reservation-conflicts-resolve-pre-merge-through-git-rebase). AIADRA Core never requires or provides a live allocator.

## Identity and lifecycle

**UUID** — Globally unique, opaque, stable identifier for an Object. Assigned at creation, never reused, never changes. Filenames, Numbers, and storage paths can change; UUID does not.

**Number** — Human-readable identifier (e.g., `P-000123`, `REQ-0014`, `DV-0007`). Stable within a project, intended for humans (UUID serves the system). Allocated through a Reservation file merged via Git; conflicts resolve at PR time. The Number is presentation, not truth.

**Revision** — A formally released state of an Object (e.g., Rev A, Rev B). Released revisions are immutable. New work happens on the next revision.

**Iteration** — A working version of an Object between releases. Mutable; not yet committed to a Revision baseline.

**Lifecycle State** — Where an Object is in its life: `in_work`, `under_review`, `released`, `superseded`, `obsolete`. State transitions follow deterministic rules.

**Released Truth** — Data belonging to a Released Revision. Immutable. Modifying it requires creating a new Revision through a controlled Change process (ECR/ECO).

## Engineering data

**Part** — A managed Object Type representing a physical, internally-designed engineering component (mechanical, electrical, or other domain). First concrete Object Type in the seed catalogue per [ADR/0005](ADR/0005-object-type-part.md). Number prefix `P-NNNNNN` by default. Carries seven TypeSpecific namespaces: `parameter:`, `design_intent:`, `feature:`, `relationship:`, `published_ref:`, `geometry_ref:` (role-discriminated: `authoring_geometry` for canonical kernel geometry, `derived_export` for D7-derived release artifacts retained on the sidecar), and `material:`. Distinguished from Component (purchased / sourced item; landed in seed via [ADR/0014](ADR/0014-object-type-component.md) as the canonical Binding Object Type) by being internally designed — Part holds authoring geometry / features; Component carries upstream binding + mirrored published_ref records.

**Assembly** — A managed Object Type representing a composition of Parts and / or sub-Assemblies as a single engineering unit. Third seed Object Type per [ADR/0007](ADR/0007-object-type-assembly.md), completing the seed catalogue. Number prefix `ASM-NNNNNN` by default. Six TypeSpecific namespaces (`parameter:`, `design_intent:`, `feature:` for assembly-level authored features only, `relationship:` for composition / mate / Assembly-spanning parameter expression records, `published_ref:`, `geometry_ref:`); no `material:` (deferred). Each occurrence of a constituent Part or sub-Assembly is a separate `composed_of` relationship record with position / orientation properties; the record id IS the occurrence id. Assembly-context relationships (`mated_to`, `parameter_expression`, in-context features) carry **occurrence-qualified endpoints** (`occurrence_ref` identifying which placed instance) — Object-only references without `occurrence_ref` mean the reusable Object definition, not one placed instance. First Type to activate the `composed_of` `acyclic_dependency` cycle policy with a write-validation closure rule (commits touching composition hard-fail if transitive closure can't be resolved). Configuration / variant semantics and compact pattern primitives are explicitly deferred to future ADRs / Schema Change Notes.

**Requirement** — A managed Object Type representing a statement of what the product must do, constrain, or guarantee. Second concrete Object Type in the seed catalogue per [ADR/0006](ADR/0006-object-type-requirement.md); first non-physical Type. Number prefix `REQ-NNNNNN` by default. Three TypeSpecific singletons under the `requirement:` block (`statement`, `category`, `default_verification_method`) plus five namespaces (`parameter:`, `acceptance_criterion:`, `design_intent:`, `relationship:`, `source:`). Category enum: `functional | performance | non_functional | interface | design_constraint | regulatory`. Default verification methods: `test | analysis | inspection | demonstration`. Verified by Tests (when TestProcedure Type lands); linked to Parts via `satisfies` and to other Requirements via `derived_from` / `refines`. The seven-namespace shape established by [Part](ADR/0005-object-type-part.md) is a template, not a quota — Requirement demonstrates selective namespace adoption (no `feature:` / `geometry_ref:` / `material:` / `published_ref:` / adapter shell).

**Component** — A managed Object Type representing a purchased / sourced / catalog item adopted from upstream into the consumer project. Fourth Object Type after the seed catalogue (Part, Requirement, Assembly), landed by [ADR/0014](ADR/0014-object-type-component.md). First **External pointer Object** operationalization of the [Promotion Rule commitment 5](TruthModelSchema.md) named non-disqualifier pattern. Number prefix `C-NNNNNN` by default. Passes the Promotion Rule via Binding lifecycle: local UUID + local lifecycle + local addressability, with the upstream binding carried entirely in the singleton `component:` TypeSpecific block. Selectively adopts five of Part's seven namespaces (`parameter:`, `design_intent:`, `relationship:`, `published_ref:`, `geometry_ref:` — `geometry_ref` restricted to `derived_export` role only); no `feature:` (Component is not internally designed); no `material:` (deferred). The singleton `component:` block carries a **discriminator-specific upstream binding**: `sourcing_discriminator` ∈ {`aiadra_catalog`, `supplier_datasheet`, `custom`} selects exactly one of `catalog_ref` (AIADRA-project upstream — uses `project_scope`), `supplier_ref` (supplier-datasheet upstream — manufacturer + part_number + datasheet_content_hash; never `project_scope`), or `custom_ref` (opaque project-policy-driven descriptor + content_hash). `binding_mode: float | fixed` with default Float; release materialization is staleness-intolerant for all three discriminators (resolve + pin integrity anchors atomically; release hard-fails without resolvable content hash). Component-owned `published_ref` records are local stable aliases with `upstream_fact_ref: "published_ref:<upstream-id>"`; release validates the full chain (mate → local pr → pinned upstream Revision → upstream pr id existence). Engineering relationships (`composed_of` target, `mated_to` endpoint, `allocates_to` target) extend to accept Component additively in the same ADR/0014 bundle bump (v0.10.0 → v0.11.0), closing prior deferrals from ADR/0010 / ADR/0011 / ADR/0013. Component as `satisfies` source deferred to future Schema Change Note. Critically: AIADRA Core hosts no Component registry, no resolution service, no live coordination per [Manifesto P11](Manifesto.md); `locator_hint` / `datasheet_url` are explicitly non-authoritative transport hints.

**SoftwareModule** — A managed Object Type representing a software module — either first-party (authored in the project's own Commonspace) or externally-sourced (Git submodule, package-registry dependency, AIADRA catalog upstream, custom). Fifth Object Type, landed by [ADR/0016](ADR/0016-object-type-software-module.md). Number prefix `SM-NNNNNN` by default. **Dual Promotion paths:** External pointer Object (Binding lifecycle) named non-disqualifier pattern when discriminator ∈ {`git_module`, `package_registry`, `aiadra_catalog`, `custom`}; direct Promotion via basic capability test when discriminator == `workspace_git`. First Object Type to invoke both Promotion paths depending on discriminator. Selectively adopts three of Part's seven namespaces (`parameter:`, `design_intent:`, `relationship:`); no `feature:` / `published_ref:` / `geometry_ref:` / `material:`. The singleton `software_module:` block carries a discriminator-specific upstream binding shape: `sourcing_discriminator` ∈ {`workspace_git`, `git_module`, `package_registry`, `aiadra_catalog`, `custom`} selects exactly one of `workspace_ref` (in-Commonspace module — repo-relative `module_path` + algorithm-qualified `commit_hash` + `tree_hash`), `git_ref` (external Git submodule — `origin_id` stable identity + non-authoritative `git_url` + optional `module_path` for subtrees + algorithm-qualified `commit_hash` and `tree_hash`), `package_ref` (package registry — `registry` + `package_name` + authoring `version_spec` separate from released-immutable `resolved_version` + `artifact_hash`), `catalog_ref` (AIADRA project upstream — same shape as Component), `custom_ref` (opaque descriptor + `content_hash`). All hash fields are **algorithm-qualified strings** (`git-sha1:<oid>`, `git-sha256:<oid>`, `sha256:<artifact-bytes>`, etc.); ADR/0016 pins this convention normatively for the first time. **Authoring intent fields** (`ref`, `version_spec`) are distinct from **released-immutable identity fields** (`commit_hash`, `resolved_version`, `artifact_hash`); working sidecar carries authoring intent only; released materialized Revisions add resolved-immutable fields. `binding_mode: float | fixed` with default Float; staleness-intolerant release per ADR/0009 §3 pattern. **Does NOT participate in `composed_of` in seed** — software composition awaits a future software-specific composition relationship (`embeds`/`depends_on`/similar); transform fields don't fit software. Participates as `allocates_to` target and as `parameter_expression` endpoint (both input and output), with the SoftwareModule-as-output authority guardrail generalizing ADR/0015 §4's Component-as-output rule (output parameter must be local/consumer-authored, not mirrored upstream). SoftwareModule as `satisfies` source deferred. Critically: AIADRA Core hosts no Git registry, no package resolver, no live coordination per [Manifesto P11](Manifesto.md); `git_url`, `datasheet_url`, `locator_hint`, and `registry` resolvers are project/adapter-local.

**Drawing** — A managed Object Type representing an engineering drawing artifact — a 2D representation of a Part or Assembly with title block, dimensions, callouts, design-intent records, and an authored canonical payload. Sixth Object Type, landed by [ADR/0017](ADR/0017-object-type-drawing.md). Number prefix `DWG-NNNNNN` by default. First **Attachment-bearing Object** operationalization of the [Promotion Rule commitment 5](TruthModelSchema.md) named non-disqualifier pattern — counterpart to ADR/0014's first External pointer Object operationalization. Selectively adopts two of Part's seven namespaces (`design_intent:`, `relationship:`); no `parameter:` / `feature:` / `published_ref:` / `geometry_ref:` / `material:`. Singleton `drawing:` block carries `title` (REQUIRED), `sheet_size`, `scale`, `projection_type` (enum `first_angle | third_angle`), `revision_block_format`, and free-form `title_block_fields` (with explicit guardrail: title-block values may mirror canonical Object metadata for rendering, but canonical metadata wins on mismatch — `title_block_fields` is rendering convenience, not a second source of truth). **New `attachment:` namespace** introduced by ADR/0017 as the template for Attachment-bearing Object Types (EvidenceArtifact and future inherit this shape). Each `attachment:` record carries `id`, `role` ∈ {`source_authoring`, `rendered_primary`, `derived_secondary`}, `media_type` (IANA), `vault_path` (Vault-Adapter-resolved locator, non-authoritative per Manifesto P11), `content_hash` (algorithm-qualified per ADR/0016 convention, authoritative integrity anchor), and `derived_from_attachment_id` (REQUIRED for derived roles; FORBIDDEN for `source_authoring`). **D7-escape is structural** — every released Drawing MUST carry at least one `source_authoring` attachment with `content_hash` resolved; derived attachments form a lineage chain that terminates at a `source_authoring` record (no dangling, no cycles). Hash-as-authority discipline; retrieved Vault bytes hard-fail on hash mismatch. Working state may have zero attachments; release materialization is the invariant trigger. Eventability: `drawing_created` / `drawing_changed` / `drawing_released` / `drawing_retired`. Participates as `allocates_to` target (a Requirement may be allocated to a drawing deliverable); future `depicts` relationship — pre-declared in [ADR/0005 §11](ADR/0005-object-type-part.md) and [ADR/0007 §11](ADR/0007-object-type-assembly.md) as Drawing → Part/Assembly, binary, `trace_graph` — is deferred to a separate relationship-type ADR. Drawing as `satisfies` source deferred. AIADRA Core hosts no Drawing registry, no Vault, no rendering service per [Manifesto P11](Manifesto.md).

**EvidenceArtifact** — A managed Object Type representing a record of evidence — what was observed, measured, simulated, or inspected. Seventh Object Type, landed by [ADR/0019](ADR/0019-object-type-evidence-artifact.md). Number prefix `EVD-NNNNNN` by default. **Second Attachment-bearing Object** Type — first reuse of [ADR/0017](ADR/0017-object-type-drawing.md)'s template, validating template reusability. Inherits the `attachment:` namespace shape, `source_authoring` / `rendered_primary` / `derived_secondary` role enum, `derived_from_attachment_id` lineage chain, algorithm-qualified `content_hash` integrity, and pre-commit resolution discipline — all verbatim from ADR/0017 — with **two EvidenceArtifact-specific specializations**: (1) **`source_authoring` MUST be the canonical evidence payload** (raw measurement log, solver result package, signed test report, lab notebook export, calibration certificate, or equivalent canonical record of the evidence collected), not setup/method files only; method files like simulation input decks may be present as additional `source_authoring` records but cannot be the only `source_authoring` (a released EvidenceArtifact must not be reconstructable as "input deck + hand-entered result values"); (2) **every `parameter:` record carries explicit lineage to supporting attachment(s)** via `fact_provenance.derived_from: ["attachment:<id>", ...]` (reusing S1's existing field); at least one entry must reference an `attachment:` record in the same sidecar; full chain: parameter → derived_from → attachment → content_hash → Vault bytes. Selectively adopts four of Part's seven namespaces (`parameter:`, `design_intent:`, `relationship:`, plus inherited `attachment:`); no `feature:` / `published_ref:` / `geometry_ref:` / `material:`. Singleton `evidence:` block carries `summary` (REQUIRED — textual canonical fact per ADR/0006's structured-text content pattern), `evidence_kind` (REQUIRED enum: `simulation | test_report | measurement | inspection | calibration_certificate | analysis | other`), `collected_at` (OPTIONAL ISO8601 timestamp), `collection_context` (OPTIONAL prose-only — guardrail against junk-drawer drift; **prose-only role partially superseded** by [ADR/0022](ADR/0022-test-execution-model.md) — the structural TestProcedure linkage is now the graph traversal `EvidenceArtifact ←produces← TestExecution →executes→ TestProcedure`; `collection_context` remains for additional prose context but is no longer load-bearing as the procedure linkage anchor). Eventability: `evidence_artifact_created` / `_changed` / `_released` / `_retired`. **No relationship-type schema extensions in ADR/0019** — Requirement-to-EvidenceArtifact citation / verification deliberately deferred to the future V&V relationship-type ADR; `allocates_to` MUST NOT be used as a temporary stand-in (it is responsibility-assignment, not V&V citation — wrong verb). `relationship:` namespace exists for future `verified_by` / `tested_against` / `cites` participation; future occurrence-qualified citations of placed instances inherit ADR/0018's `occurrence_context` shape. EvidenceArtifact as `satisfies` source deferred. AIADRA Core hosts no evidence registry, no simulation runner, no test-instrument coordinator, no Vault per [Manifesto P11](Manifesto.md).

**TestProcedure** — A managed Object Type representing a reusable engineering test / verification method specification — a documented procedure that, when executed, produces evidence about an engineering Object. Eighth Object Type, landed by [ADR/0020](ADR/0020-object-type-test-procedure.md). Number prefix `TST-NNNNNN` by default. **Third Attachment-bearing Object** Type — second reuse of [ADR/0017](ADR/0017-object-type-drawing.md)'s template after [ADR/0019](ADR/0019-object-type-evidence-artifact.md), validating template reusability with a different per-Type `source_authoring` specialization. Inherits the `attachment:` namespace shape, `source_authoring` / `rendered_primary` / `derived_secondary` role enum, `derived_from_attachment_id` lineage chain, algorithm-qualified `content_hash` integrity, and pre-commit resolution discipline — all verbatim from ADR/0017 — with **one TestProcedure-specific specialization**: `source_authoring` MUST be the **canonical procedure document** (signed test plan, standard operating procedure (SOP), test script, runbook, regulatory protocol document, or equivalent canonical record of the method to be executed), not a metadata-only stub or summary. A released TestProcedure must not be reconstructable as "a title + a few notes" without a canonical method specification attached and named. Selectively adopts three of Part's seven namespaces (`parameter:`, `design_intent:`, `relationship:`, plus inherited `attachment:`); no `feature:` / `published_ref:` / `geometry_ref:` / `material:` / `source:` in seed (procedure origin / upstream-standard provenance can be captured in `attachment:` metadata or `design_intent:` prose; structured `source:` extension deferred). Singleton `test_procedure:` block (snake_case — divergence from ADR/0006 line 396's run-together `testprocedure:` pre-declaration, pinned per [ADR/0016](ADR/0016-object-type-software-module.md)'s `software_module:` precedent) carries `title` (REQUIRED), `verification_method` (REQUIRED enum: `test | analysis | inspection | demonstration` — verbatim from [ADR/0006 §7](ADR/0006-object-type-requirement.md); cross-check anchor for the future `verifies` relationship-type ADR), `applicability_summary` (OPTIONAL prose — guardrail against junk-drawer drift; structured applicability deferred), `expected_outputs_summary` (OPTIONAL prose — authoring scaffolding; structured EvidenceArtifact references land via future `cites`). **No `test_kind` enum in seed.** TestProcedure `parameter:` records are **nominal design facts** (typical `fact_provenance.category: "human_input"`), NOT derived measurements — **no `fact_provenance.derived_from` lineage discipline** (that lives on EvidenceArtifact). Eventability: `test_procedure_created` / `_changed` / `_released` / `_retired`. **Participates as `allocates_to` target** (ADR/0020 §5) — additive endpoint extension to [ADR/0013](ADR/0013-relationship-type-allocates-to.md); **explicit wrong-verb authoring guardrail**: only procedure-deliverable Requirements ("the project shall publish a documented procedure") may be allocated to a TestProcedure; product Requirements awaiting verification ("bracket shall withstand 5400 N") target the future `verifies` edge instead (schema cannot semantically distinguish; tooling-aided diagnostic). Future `verifies` (TestProcedure → Requirement), `tested_against` (Part / Assembly → TestProcedure), and `cites` (TestProcedure → EvidenceArtifact) deferred to V&V relationship-type ADR — `relationship:` namespace exists for future population. TestProcedure as `satisfies` source deferred. **Partial supersession** of [ADR/0006 §"Consequences" line 397](ADR/0006-object-type-requirement.md)'s "test procedure body" forward reference: canonical procedure body lives in `source_authoring` attachment, not sidecar structured text; structured per-step records deferred to Schema Change Note. Test execution model (events / EvidenceArtifact lineage back to executed TestProcedure UUID) deferred — **resolved by [ADR/0022](ADR/0022-test-execution-model.md)** which lands TestExecution as the ninth Object Type plus three execution-instance relationships (`executes` / `executed_on` / `produces`) carrying the atomic procedure-revision + executed-run + produced-evidence + tested-Object binding. AIADRA Core hosts no procedure registry, no test runner, no instrument coordinator, no Vault, no certification-authority bridge per [Manifesto P11](Manifesto.md).

**TestExecution** — A managed Object Type representing a specific historical run of a TestProcedure against one or more Part / Assembly Objects, producing zero or more EvidenceArtifact records. Ninth Object Type, landed by [ADR/0022](ADR/0022-test-execution-model.md). Number prefix `TEX-NNNNNN` by default. **Fourth Attachment-bearing Object** Type — third reuse of [ADR/0017](ADR/0017-object-type-drawing.md)'s template after [ADR/0019](ADR/0019-object-type-evidence-artifact.md) and [ADR/0020](ADR/0020-object-type-test-procedure.md), validating template reusability a third time with a TestExecution-specific `source_authoring` specialization. **First execution-instance Object Type** — distinct from design-intent Object Types (Part / Requirement / Assembly) and Attachment-bearing canonical-record Object Types (Drawing / EvidenceArtifact / TestProcedure). Records *what happened in a specific historical event* rather than *what the engineering intent is*. Inherits the `attachment:` namespace shape, role enum, `derived_from_attachment_id` lineage chain, algorithm-qualified `content_hash` integrity, and pre-commit resolution discipline — all verbatim from ADR/0017 — with **TestExecution-specific specialization**: `source_authoring` MUST be the **canonical record of the execution event** (raw instrument output, signed inspector report, automated test framework output, video log, or equivalent canonical record of what occurred during the run), not a metadata-only stub. Selectively adopts three of Part's seven namespaces (`parameter:`, `design_intent:`, `relationship:`, plus inherited `attachment:`); no `feature:` / `published_ref:` / `geometry_ref:` / `material:` / `source:` in seed. **Parameter lineage discipline applies** (parallel to EvidenceArtifact per [ADR/0019 §4](ADR/0019-object-type-evidence-artifact.md)) — TestExecution parameters are observed measurements / observed values from the run record, NOT nominal design facts (the latter live on TestProcedure with no lineage discipline); every `parameter:` record carries `fact_provenance.derived_from` with at least one `"attachment:<id>"` entry. Singleton `test_execution:` block carries `executed_on_date` (REQUIRED ISO 8601 date), `execution_status` (REQUIRED enum: `completed | aborted | inconclusive` — first introduction of this taxonomy; pass/fail framing is a V&V judgment relative to verified Requirement criterion, NOT on the execution record, per [ADR/0019 §"Alternatives §E1"](ADR/0019-object-type-evidence-artifact.md) carry-forward), `operator_identifier` (OPTIONAL free-form string — project-policy whether name / role / AI agent id per [Manifesto P13](Manifesto.md)), `instrument_identifier` (OPTIONAL free-form string), `environmental_conditions_summary` (OPTIONAL prose). Eventability: `test_execution_created` / `_changed` / `_released` / `_retired` — **partial supersession** of [ADR/0020 §"Consequences"](ADR/0020-object-type-test-procedure.md) `test_execution_started` / `_completed` event-payload sketch (the standalone event-payload framing is replaced by the Object event taxonomy now that TestExecution is first-class). **Participates as source of three new execution-instance relationships**: `executes` (TestExecution → TestProcedure, exactly 1 record at release), `executed_on` (TestExecution → Part | Assembly, ≥1 records at release), `produces` (TestExecution → EvidenceArtifact, ≥0 records with status-sensitive normative refinement — `completed` SHOULD ≥1, `aborted` MAY 0, `inconclusive` MAY 0 or ≥1). Does NOT participate in design-intent trace relationships (`satisfies`, `verifies`, `tested_against`, `cites`, `allocates_to`, etc.); the execution-instance relationships are the entire participation surface. **First execution-instance relationship category** — all three new relationships are **Fixed-only (Float forbidden)**, with `endpoints[0].revision_id` REQUIRED unconditionally and cross-project endpoints opt OUT (event-locality dimension — execution events are intrinsically local). AIADRA Core hosts no test runner, no instrument coordinator, no Vault, no execution registry per [Manifesto P11](Manifesto.md).

**`mated_to`** — Geometric / topological relationship: two features (faces / axes / points / planes) on placed Part / Assembly occurrences constrained per a mate type. First geometric / topological relationship pinned by [ADR/0011](ADR/0011-relationship-type-mated-to.md); third occupant of the bundle's `relationship/<type>.schema.json` directory. **Undirected multi-endpoint serialization** — both endpoints serialized explicitly; the owning Assembly is the storage carrier (not a semantic endpoint). Seed mate-type taxonomy: `coincident`, `concentric`, `parallel`, `perpendicular`, `distance`, `angle`, `tangent`, `planar` (eight types; `lock` and kinematic mates deferred). Mate-type-specific properties: `value_mm` REQUIRED for `distance` (finite, `>= 0`); `value_deg` REQUIRED for `angle` (finite, `0 <= value_deg <= 180`); `aligned` REQUIRED on six orientation-meaningful types. Each endpoint takes one of two mutually-exclusive forms: **Form A** (`fact_ref: published_ref:<id>` — preferred, release-capable) or **Form B** (`selector: { ... }` layered topological selector — working / transitional, requires `requires_validation`). Endpoints carry stable local `id`s per [S0 commitment 7](TruthModelSchema.md#7-list-addressability-rule) (multi-endpoint stable-id pattern); endpoint order non-semantic. **Indirect-binding** — no relationship-level `binding` field; endpoint binding inherited from occurrence-path resolution per [ADR/0010 §3](ADR/0010-relationship-type-composed-of.md) (Assembly-owned) or carrier Part Revision (Part-owned within-Part); endpoint `revision_id` is cross-check (hard-fail on mismatch), never authority. Cycle policy `undirected_constraint_graph` — first relationship type to activate this cycle class at runtime; closed loops permitted; over-constraint is solver concern (not cycle violation). Direct cross-project endpoints NO ([ADR/0008 §4](ADR/0008-cross-project-object-identity.md) engineering-structure default) — consumer Assemblies route through local Components. Release-bound cross-Object endpoints MUST use Form A unless `requires_validation` invoked per S3 §11 narrow exception; within-Part mates not subject to this rule. Mate-satisfaction validation at release: every materialized mate must evaluate true against materialized occurrence transforms; contradictory / unsatisfied mates hard-fail release.

**`composed_of`** — Engineering-graph structural / compositional relationship: an Assembly contains a Part or sub-Assembly as one occurrence. First structural relationship type pinned by [ADR/0010](ADR/0010-relationship-type-composed-of.md); second occupant of the bundle's `relationship/<type>.schema.json` directory. Source-anchored on the Assembly; serialization is implicit source (the owning Assembly sidecar) + single-entry `endpoints` array (target Part or Assembly). Each record IS the occurrence per [ADR/0007 §1](ADR/0007-object-type-assembly.md); the record's stable `id` is the occurrence id referenced by `occurrence_ref` on assembly-context relationships. Carries `occurrence:` sub-object with `instance_name?` and `transform` (position + unit quaternion). Position in canonical millimeters (`position_mm` field name encodes the unit); rotation as `quaternion_xyzw` with `[x, y, z, w]` convention and hard normalization invariant (`|q|² ∈ [1 - 1e-6, 1 + 1e-6]`). No scale; identity transform written explicitly. Cycle policy `acyclic_dependency` — first relationship type to engage [ADR/0007 §5](ADR/0007-object-type-assembly.md)'s write-validation closure rule at runtime; self policy `self_forbidden`; default binding `float`. Direct cross-project endpoints NO ([ADR/0008 §4](ADR/0008-cross-project-object-identity.md) engineering-structure default) — consumer Assemblies route through local Components. Nested occurrence paths (`rel_composed_wrist/rel_composed_servo`) use prefix-free bare-id slash-separated syntax with binding-aware per-segment resolution; supersedes [ADR/0007 §2](ADR/0007-object-type-assembly.md)'s worked-example `relationship:<id>` form. Configuration / variants and pattern primitives deferred per ADR/0007.

**`satisfies`** — Engineering-graph trace relationship: a Part or Assembly claims it satisfies a Requirement as a whole, including all acceptance criteria present in that Requirement Revision. First relationship type pinned by [ADR/0009](ADR/0009-relationship-type-satisfies.md); first occupant of the bundle's `relationship/<type>.schema.json` directory. Source-anchored on the Part or Assembly's `relationship:` namespace; serialization is implicit source (the owning sidecar Object) + single-entry `endpoints` array carrying the target Requirement only. Binary at the semantic layer; cycle policy `trace_graph`; self policy `self_forbidden`; default binding `float`. Direct cross-project endpoints permitted ([ADR/0008 §4](ADR/0008-cross-project-object-identity.md) trace-relationship opt-in) — a consumer Part / Assembly may satisfy an external Requirement (e.g., a regulatory clause published as a catalog Requirement) without routing through a local Binding Object. Float cross-project endpoints resolve to the external Requirement's current released Revision (never the external project's working sidecar); release materialization is staleness-intolerant and pins `revision_id` + `revision_content_hash` per [ADR/0008 §6](ADR/0008-cross-project-object-identity.md). The exception does NOT generalize to product-structure relationships (`composed_of`, `mated_to`, etc., still target local Binding Objects). Partial / criterion-scoped satisfaction not representable in the seed schema; **criterion-level addressing remains deferred for `satisfies` specifically** even after [ADR/0021](ADR/0021-relationship-types-v-and-v.md) reopened the broader deferral — ADR/0021 lands the `endpoints[].fact_ref` primitive at the trace-relationship base schema level but `satisfies` does NOT opt in (per ADR/0021 §6's per-relationship-schema-opt-in discipline); a separate Schema Change Note can land `satisfies` retrofit if production case surfaces. `verifies` and `cites` per ADR/0021 are the first opt-ins.

**`derived_from`** — Engineering-graph trace relationship: a Requirement is decomposed / refined out of another Requirement during requirements analysis. Fourth relationship type pinned by [ADR/0012](ADR/0012-relationship-types-derived-from-and-refines.md), landing in a combined ADR with `refines`; fourth occupant of the bundle's `relationship/<type>.schema.json` directory. Source-anchored on the source Requirement's `relationship:` namespace; serialization is implicit source (the owning Requirement sidecar) + single-entry `endpoints` array carrying the target Requirement only. Binary at the semantic layer; cycle policy `trace_graph` — partial supersession of [ADR/0006 §"Decision 12"](ADR/0006-object-type-requirement.md)'s provisional `acyclic_dependency`; cycles are graph-class-valid but semantically suspicious, so tooling may warn without schema hard-fail. Self policy `self_forbidden`; default binding `float`. Multiple parents permitted (a Requirement may be `derived_from` two upstream Requirements that together produced it). Direct cross-project endpoints permitted per [ADR/0008 §4](ADR/0008-cross-project-object-identity.md) trace-relationship opt-in (regulatory-clause derivation lineage); Float external semantics inherited verbatim from [ADR/0009 §3](ADR/0009-relationship-type-satisfies.md). All thirteen base trace-relationship pattern fields inherited from ADR/0009; no new pattern fields declared. Endpoint Type scope Requirement → Requirement only in seed; Part → Part for catalog / variant lineage deferred until Configuration ADR machinery lands.

**`refines`** — Engineering-graph trace relationship: a Requirement is a more specific expression of another Requirement — added precision, narrowed scope, added constraint. Fifth relationship type pinned by [ADR/0012](ADR/0012-relationship-types-derived-from-and-refines.md), landing in a combined ADR with `derived_from`; fifth occupant of the bundle's `relationship/<type>.schema.json` directory. Shape-identical to `derived_from` at seed (same source-anchored asymmetric binary serialization; same `trace_graph` cycle class with partial ADR/0006 §"Decision 12" supersession; same `self_forbidden` policy; same default Float binding; same direct cross-project opt-in for upstream standards-clause refinement). Semantic distinction lives in this Glossary entry: `refines` is *increased specificity in the same direction*, not strict tree-decomposition. Use `refines` when a sub-Requirement narrows or specializes a parent (added test threshold, narrower applicability scope, additional constraint) without representing a decomposition into independent children. Multiple parents permitted but uncommon. Criterion-level refinement deferred until verification taxonomy lands ([ADR/0009 §2](ADR/0009-relationship-type-satisfies.md) pattern).

**`allocates_to`** — Engineering-graph trace relationship: a Requirement is allocated to a Part or Assembly responsible for fulfilling it. Sixth relationship type pinned by [ADR/0013](ADR/0013-relationship-type-allocates-to.md); sixth occupant of the bundle's `relationship/<type>.schema.json` directory. Closes the four-relationship trace family from [ADR/0006 §"Decision 12"](ADR/0006-object-type-requirement.md) (`satisfies`, `derived_from`, `refines`, `allocates_to`). Source-anchored on the source Requirement's `relationship:` namespace; serialization is implicit source (the owning Requirement sidecar) + single-entry `endpoints` array carrying the target Part or Assembly only. Binary at the semantic layer; cycle policy `trace_graph` (already correct in ADR/0006 §12 — no supersession); self policy `self_forbidden`; default binding `float`. Endpoint Type scope at seed: `Part | Assembly` (per ADR/0013, mapping ADR/0006's "Part / Subsystem" forward to the current seed catalogue; Subsystem is not a promoted Type). Additively extended by subsequent ADRs: `Component` per ADR/0014, `SoftwareModule` per ADR/0016, `Drawing` per ADR/0017, `TestProcedure` per ADR/0020 — current target Type union is `Part | Assembly | Component | SoftwareModule | Drawing | TestProcedure` (**EvidenceArtifact excluded** per [ADR/0019 §"Alternatives §C"](ADR/0019-object-type-evidence-artifact.md) — emergent from execution, wrong verb). **Deliverable-vs-emergent governing principle** for target inclusion: committed-to-produce deliverables MAY be `allocates_to` targets; emergent records MAY NOT. The TestProcedure target carries an explicit **wrong-verb authoring guardrail** per [ADR/0020 §5](ADR/0020-object-type-test-procedure.md): only procedure-deliverable Requirements ("project shall publish a documented procedure") may be allocated to a TestProcedure; product Requirements awaiting verification target the future `verifies` edge instead (the schema cannot semantically distinguish the two `allocates_to` shapes; tooling may surface as a non-blocking diagnostic). **Direct cross-project endpoints NO** — first trace-relationship to opt OUT of [ADR/0008 §4](ADR/0008-cross-project-object-identity.md)'s per-type exception. Rationale: the cross-project trace exception was justified by the external-regulatory-Requirement use case; that justification does not transfer when the target is a deliverable Object (Part / Assembly). Cross-project deliverable adoption routes through local Binding Objects (Component, when that Type lands) per [ADR/0008 §3](ADR/0008-cross-project-object-identity.md); cross-project `allocates_to` is deferred to a future Schema Change Note. Establishes the **target-Type-governs-cross-project-policy** precedent for relationship-type ADRs. Distinct from `satisfies` (the reverse arrow): `allocates_to` is top-down responsibility assignment authored on the Requirement sidecar; `satisfies` is bottom-up satisfaction claim authored on the Part/Assembly sidecar. Both records can coexist for the same Req–Part pair. ADR/0013 partially clarifies ADR/0006 §C3 line 109's "subsystems (`allocates_to`)" wording (which was readable as subsystem-as-source) to mean Requirements may *author* `allocates_to` records whose targets are subsystem-like Objects.

**`depicts`** — Engineering-graph trace / documentation relationship: a Drawing documents an engineering Object (Part, Assembly, or Component). Eighth relationship type pinned by [ADR/0018](ADR/0018-relationship-type-depicts.md); eighth occupant of the bundle's `relationship/<type>.schema.json` directory. Closes the pre-declarations from [ADR/0005 §11](ADR/0005-object-type-part.md) and [ADR/0007 §11](ADR/0007-object-type-assembly.md). Source-anchored on the Drawing's `relationship:` namespace; implicit source (the owning Drawing sidecar) + single-entry `endpoints` array carrying the target Object. Binary at the semantic layer; cycle policy `trace_graph`; self policy `self_forbidden`; default binding `float`. Endpoint Type scope: source `Drawing`; target `Part | Assembly | Component` in seed (`SoftwareModule` excluded — no geometry to depict; `Drawing`-to-`Drawing` out of scope). **Direct cross-project endpoints NO** — target-Type-governs precedent from [ADR/0013](ADR/0013-relationship-type-allocates-to.md); cross-project documentation routes through local Component Binding Object. **Occurrence-qualified target via explicit `occurrence_context`** — first source-anchored asymmetric binary trace relationship whose source (Drawing) lacks implicit composition visibility into the target, necessitating an explicit Assembly resolver root. Target endpoint may carry `occurrence_context: { object_uuid, revision_id? }` paired with `occurrence_ref` (both present or both absent — schema-coupled XOR forbidden). When occurrence-qualified, the Drawing depicts a specific placed instance inside the context Assembly; release pins both `occurrence_context.revision_id` (Assembly composition-path authority) and terminal `endpoint.revision_id` (depicted Object's resolved Revision); terminal `object_uuid` cross-checks against path resolution. Sets the precedent for any future trace relationship that documents placed instances from outside the containing Assembly's namespace. **Component-target authority guardrail:** when target is a Component, the Drawing documents the local Component Binding Object's identity and approved upstream binding — Drawing's `attachment.content_hash` (local-payload integrity) and Component's upstream `revision_content_hash` / `datasheet_content_hash` / etc. are distinct integrity anchors; the `depicts` relationship is the trace link between them. Multiple `depicts` records per Drawing permitted; no record-level "primary subject" flag in seed (consumer-policy convention). View / region semantics (cross-section planes, callout regions, exploded-view transforms, coverage) deferred to Schema Change Note. Inherits ADR/0009's thirteen base trace-relationship pattern fields. Seventh relationship type pinned by [ADR/0015](ADR/0015-relationship-type-parameter-expression.md); seventh occupant of the bundle's `relationship/<type>.schema.json` directory. **First fact-level endpoint addressing** (endpoints are parameter addresses `<object_uuid>:parameter:<id>`, not Object addresses); **first asymmetric multi-endpoint serialization** (counterpart to ADR/0011's undirected/symmetric `mated_to` shape) — separate `output_endpoint` (singleton) + `input_endpoints` (list with stable local ids). Source-anchored uniformly on the Object owning the **output parameter** — within-Object expressions live on that Object; skeleton-driven propagation lives on the downstream Object (not the master); Assembly-owned aggregates (`ASM.total_mass_kg = sum(child.mass_kg)`) live on the Assembly because the aggregate parameter is on the Assembly itself; Assembly-computes-constituent **forbidden** (no occurrence-local parameter model; `output_endpoint.occurrence_ref` schema-rejected). Cycle policy `acyclic_dependency` (declared in ADR/0005 §11, ADR/0007 §11, TruthModelSchema S3 commitment 13); write-validation closure walks `output_parameter → input_parameter` edges project-wide. **Indirect-binding** (no relationship-level `binding`; endpoint resolution delegated to address mechanism — within-Object via container Revision, cross-Object via occurrence-path per ADR/0010 §3). **Direct cross-project endpoints NO** (engineering-structure default per ADR/0010 §"Pattern inheritance"); cross-project parameter references route through local Component. Endpoint Type union: Part, Requirement, Assembly, Component (per ADR/0014 §4) — for both output and input endpoints. **Component-as-output authority guardrail:** output parameter must be local/consumer-authored on the Component, not a mirrored upstream/datasheet field. **Expression payload:** discriminator-driven `{form, language, value, variables}`. Seed `form: formula_string`. `language` is consumer-policy / adapter identifier (per Manifesto P11 — AIADRA Core does not enumerate languages); `value` is opaque text in that language; `variables[]` map declares the canonical `symbol → input_endpoint_id` binding. **Schema-enforced bijection:** every `variables[].input_endpoint_id` matches exactly one `input_endpoints[].id`; every `input_endpoints[].id` is referenced by exactly one `variables[].input_endpoint_id`. No dangling references; no unused inputs; no `allow_unused` escape hatch in seed. Together this makes the dependency set canonical for cycle detection without Core having to parse the formula text. Future `expression.form` values (`structured_tree`, `external_computation`) deferred. Use cases: skeleton-driven design (master parameters propagate to downstream Objects), Assembly mass / cost roll-ups, interpart constraints, Requirement-driven sizing.

**`verifies`** — Engineering-graph V&V trace relationship: a TestProcedure verifies a Requirement (the procedure is the verification method for that Requirement). **`tested_against`** — Engineering-graph V&V trace relationship: a Part or Assembly was tested against a TestProcedure. **`cites`** — Engineering-graph V&V citation relationship: a Requirement cites an EvidenceArtifact as supporting basis for satisfaction. Source-anchored on the TestExecution's `relationship:` namespace; implicit source + single-entry `endpoints` array carrying the target TestProcedure only. Binary; cycle policy `trace_graph`; self policy `self_forbidden`. **Default binding: `fixed` (Float forbidden — pattern-setting per [ADR/0022 §6](ADR/0022-test-execution-model.md)):** execution records are historically anchored; "this past run tracks the procedure's current Revision" is semantic nonsense. Each schema rejects Float. `endpoints[0].revision_id` REQUIRED unconditionally. **Cardinality at release: exactly 1** `executes` record per released TestExecution (Layer-2 hard-fail otherwise — a TestExecution represents one run of one procedure; two procedures executed back-to-back are two TestExecutions). Endpoint Type scope: source `TestExecution`; target `TestProcedure`. **Direct cross-project endpoints NO** — target-Type-governs per [ADR/0013](ADR/0013-relationship-type-allocates-to.md); event-locality dimension reinforces (execution events are intrinsically local). No criterion-level addressing (no Requirement endpoint).

**`executed_on`** — Engineering-graph execution-instance relationship: a TestExecution was executed against one or more specific Part or Assembly Objects at specific Revisions. Thirteenth relationship type pinned by [ADR/0022](ADR/0022-test-execution-model.md); thirteenth occupant of the bundle. Source-anchored on the TestExecution's `relationship:` namespace; implicit source + single-entry `endpoints` array per record (multi-record list for multi-specimen runs). Binary; cycle policy `trace_graph`; self policy `self_forbidden`. **Default binding: `fixed` (Float forbidden** per ADR/0022 §6). `endpoints[0].revision_id` REQUIRED unconditionally. **Cardinality at release: ≥1** `executed_on` records per released TestExecution (Layer-2 hard-fail at 0 — a run with no tested Object is meaningless). Multiple specimens in a shared fixture is the multi-record case; each tested Object gets its own record. Endpoint Type union (seed): source `TestExecution`; target `Part | Assembly`. Component / SoftwareModule source extension deferred per [ADR/0022 §"Decision §10"](ADR/0022-test-execution-model.md). **Direct cross-project endpoints NO** — target-Type-governs + event-locality. No criterion-level addressing.

**`produces`** — Engineering-graph execution-instance relationship: a TestExecution produces zero or more EvidenceArtifact records as outputs of the run. Fourteenth relationship type pinned by [ADR/0022](ADR/0022-test-execution-model.md); fourteenth occupant of the bundle. Source-anchored on the TestExecution's `relationship:` namespace; implicit source + single-entry `endpoints` array per record (multi-record list for multi-evidence runs). Binary; cycle policy `trace_graph`; self policy `self_forbidden`. **Default binding: `fixed` (Float forbidden** per ADR/0022 §6). `endpoints[0].revision_id` REQUIRED unconditionally. **Cardinality at release: ≥0 globally with status-sensitive normative refinement** (first introduction of status-sensitive cardinality in the catalogue): `execution_status: completed` SHOULD have ≥1 `produces` records — Layer-2 emits a non-blocking diagnostic if 0 (legitimate exception: inspection-style runs whose canonical record is the inspector's signed declaration attached to the TestExecution itself); `aborted` MAY 0; `inconclusive` MAY 0 or ≥1 (diagnostic if 0). Future Schema Change Note may escalate completed-case to MUST. Endpoint Type scope: source `TestExecution`; target `EvidenceArtifact`. **Direct cross-project endpoints NO** — target-Type-governs + event-locality (consumer projects citing upstream evidence via [`cites`](#cites) per ADR/0021 §4 is the established cross-project shape for upstream evidence). No criterion-level addressing. **Inverse view `produced_by`** is graph-derivable via acceleration cache per [ADR/0001 §3](ADR/0001-storage-substrate.md); not authored as a separate relationship type (same posture as `where-used` / `composes` / `verified_by`). **The chain that resolves the [ADR/0021](ADR/0021-relationship-types-v-and-v.md) deferred Part / Assembly → EvidenceArtifact direct edge by declining-to-add:** `Part →tested_against→ TestProcedure ←executes← TestExecution →produces→ EvidenceArtifact` carries the linkage with full execution-instance binding.

**Design Intent** — The "why" behind a feature: purpose, role, what it depends on, what depends on it, what must not change without review. Stored on the feature as structured data, not only in human memory. Example: a hole is not just a circular cut — it is `M8 clearance for MTR-0007 mounting per REQ-014`.

**Parameter** — A named, typed input that defines an aspect of an Object (e.g., `plate_thickness_mm = 6`). The preferred surface for AI modification: same value in, same downstream effect out.

**Provenance** — For every fact in the system: where did it come from? Categories include `released_fact`, `computed_result`, `imported_supplier_data`, `human_input`, `ai_inference`, `ai_proposal`. The AI is required to distinguish these.

**Uncertainty Label** — A confidence/maturity tag on a fact: `verified`, `computed`, `estimate`, `requires_validation`, `stale`. Lets consumers (humans and AI alike) know what trust level applies.

## Records and storage

**Sidecar** — A structured, human-readable, machine-validatable metadata file (format: the AIADRA YAML Profile, settled in [ADR/0002](ADR/0002-canonical-format.md)) associated with a managed artifact. Holds the **current authoritative state** of the Object. Diffable in Git, reviewable in pull requests, readable by AI agents without opening heavy binary files.

**AIADRA YAML Profile** — The strict YAML 1.2 dialect AIADRA Core's parser enforces on every YAML-shaped canonical artifact (sidecar, Revision, Reservation): YAML 1.2 only; one managed artifact per file (cardinality scoped per kind — sidecar = one Object; Revision = one frozen Object snapshot; Reservation = one Number prefix's allocations); all ambiguous scalars (UUIDs, Numbers, version strings, anything coercible to bool) quoted; no anchors, aliases, merge keys, or custom tags; duplicate keys rejected; JSON Schema validation at every read. The duplicate-key rejection is load-bearing for Reservation conflict detection per [ADR/0004 §7](ADR/0004-number-allocation.md). Enforcement is split between AIADRA Core's parser (structural rules including duplicate-key rejection) and a token-level linter (the quoting rule, which JSON Schema cannot catch post-parse, since the parser has already resolved the scalar). Settled in [ADR/0002](ADR/0002-canonical-format.md); cardinality generalized per [ADR/0004](ADR/0004-number-allocation.md).

**Event** — A structured, append-only record of approved transitions: object created, parameter changed, revision released, ECO approved, AI proposal accepted, validation failed. Events carry provenance and link to the Transaction that produced them. Stored as JSONL, one event per line (settled in [ADR/0002](ADR/0002-canonical-format.md)).

**Sidecar / event invariant** — Sidecars hold current authoritative object state; events record approved transitions and provenance. If they disagree, validation fails — neither silently wins. The invariant is enforced at commit time: folding the event log must produce a state consistent with the sidecars (Manifesto Principle 10).

**Acceleration Cache** — A local derived index (DuckDB or SQLite) that supports parametric, graph, and where-used queries at interactive speed. Per-clone, rebuildable from canonical text artifacts, never canonical, never shared, never networked.

**Release Manifest** — The structured document defining a Release: every Object UUID and Revision in scope, every artifact hash, every validation outcome, every approval signature. Stored as deterministic JSON — sorted keys, canonical numeric serialization, normalized whitespace — so manifests are content-hashable and signable (settled in [ADR/0002](ADR/0002-canonical-format.md)).

## Change and release

**Transaction** — A bracketed, atomic, reversible unit of change. Lifecycle: `begin → modify → recompute → validate → compare → human approval → commit-or-rollback`. Every AI-driven change happens inside a Transaction. Failed Transactions leave no trace on canonical product truth, but may be recorded in an operational audit log along with their proposed changes and validation results.

**Validation** — Rule-based, deterministic checking of the model against constraints: required metadata present, all references resolve, BOM is fresh, released objects unmodified, requirement-test traceability complete, artifact hashes match, **sidecar/event invariant holds**. Validation is engineering discipline, not AI opinion.

**Where-Used** — A query returning every Object that depends on a given Object. Generated deterministically from the dependency graph. Essential AI infrastructure: "what breaks if I change this?"

**Change-order pipeline** — The mechanism by which writes promote from Workspace to Commonspace: a branch is pushed, a Pull Request opened (the ECR/ECO), impact analysis and validation results attached, maintainers review, the PR merges into a protected branch. Same machinery for AI-authored and human-authored changes (Manifesto Principles 5, 8, 13).

**ECR (Engineering Change Request)** — A proposal that something needs to change, with rationale. Captured as a Pull Request (or Issue, when earlier-stage) in the Git host's interface. Does not by itself modify Commonspace.

**ECO (Engineering Change Order)** — An approved, scoped change carrying the actual modifications, impact analysis, validation results, and approvals. Captured as a Pull Request that has cleared the change-order pipeline.

**Release** — A formally controlled engineering baseline: a frozen, reproducible snapshot of object revisions, vault artifact hashes, BOMs, drawings, exports, software versions, electrical files, DV evidence, known issues, and approval records. More than a tag — a Release is reconstructable years later.

**BOM (Bill of Materials)** — Generated, not authored. The list of purchased and made items required to build a product (or sub-assembly), derived from the Product Truth Model at a given Revision or Release.

## Planning and process

**Ring** — A unit of planning work, organized concentrically around the Product Truth Model. Ring 0 = foundation docs (Manifesto, Glossary, Architecture, ADR log, Open Questions). Ring 1 = core design specs. Ring 2 = interface contracts. Ring 3 = control layer. Ring 4 = the Wedge. Ring 5 = implementation roadmap. See [Discussions/20260517/Claude1.md](Discussions/20260517/Claude1.md).

**Wedge** — The smallest end-to-end vertical slice that exercises all architectural layers. Used to stress-test the architecture by building the minimum viable end-to-end loop. **Current scope (clarified by [ADR/0023](ADR/0023-wedge-spike-scope-and-runtime.md))**: *one Part + one Requirement + one named parameter on the Part + one `satisfies` relationship (Part → Requirement) + the minimum coherent sidecar / event-log / Revision artifact set per ADRs [0005](ADR/0005-object-type-part.md) / [0006](ADR/0006-object-type-requirement.md) / [0009](ADR/0009-relationship-type-satisfies.md) (two sidecars at working state; events `part_created` / `requirement_created` / `relationship_created` / `parameter_changed` / `part_released` / `requirement_released`; immutable Revision copies at release; one Release Manifest pinning Part + Requirement Revisions + materialized satisfies + validation outcomes + event-log boundary) + one AI Transaction modifying the parameter (lifecycle: begin → modify → recompute → validate → human approval → commit-or-rollback per [Manifesto P5](Manifesto.md)) + one deterministic validation against the Requirement.* The old singular-count phrasing (*"one sidecar / one event-log entry"*) was a shorthand from before [ADR/0005](ADR/0005-object-type-part.md) / [ADR/0006](ADR/0006-object-type-requirement.md) / [ADR/0009](ADR/0009-relationship-type-satisfies.md) pinned the concrete artifact mechanics; ADR/0023 clarifies it without expanding the Wedge's scope ambition (still Tier-S; still single Part-Requirement pair; still one parameter; still one Transaction).

**ADR (Architecture Decision Record)** — A short document recording a single load-bearing architectural decision: context, alternatives considered, decision, rationale, consequences. ADRs are the canonical record when they conflict with the Manifesto or design docs.

**Spike** — Throwaway prototype code written to test a design assumption. Allowed in any Ring; explicitly not the same as production implementation. Spikes are how design choices meet reality before getting baked in.

**Open Questions Register** — The living list of unresolved architectural and scoping questions. Each entry has a status: `under-investigation`, `deferred-to-ring-X`, `accepted-as-unresolved`, or `resolved` (with link to ADR).

**Scale targets** — The S / M / L / XL tier ladder defined in the Manifesto. AIADRA Core is architecturally compatible with Tier L from day one, operationally smooth at Tier M, with the Wedge at Tier S; Tier XL (enterprise PLM) is out of scope. Scale-sensitive decisions are bucketed as *decide-early-and-probe*, *design-with-scale-in-mind*, or *defer-with-acknowledgement*.
